
## 2. Алгоритм

Расчёт — детерминированный конвейер (`ru.heatnet.dit.engine.core.Pipeline`, in-process).
Все справочники, тарифы и правила — во внешнем конфиге
`app/src/main/resources/reference.yaml`, **не в коде** (§2.14): при выдаче
техприложения правится только YAML.

### 2.1. Загрузка и граф существующей сети

- Потоковый парсинг входного GeoJSON (Jackson streaming) — файл до 3 ГБ
  не поднимается в память целиком. СК формализованы техприложением: вход
  строго EPSG:4326 (объявленная CRS валидируется, иная отклоняется), все
  расчёты — в EPSG:32637 через собственную реализацию UTM (ряды Снайдера,
  расхождение с pyproj ~0,1 мм).
- Из сегментов и камер строится граф существующей сети; цепочки
  `next_object_id` дают направление «к источнику» — используется для
  оценки реконструкции (§2.6).

### 2.2. Весовая сетка и ограничения (§2.5)

Область расчёта растеризуется с шагом `grid_cell_m` (5 м). Каждая ячейка
получает вес из зон ограничений входного набора:

По техприложению видов правил ровно два — категории «пересечение
с условиями» нет:

- `forbidden` / `min_distance` — запрет: ячейка непроходима; для
  `min_distance` непроходим буфер `min_distance_m` вокруг объекта;
- `special_passage` — спецпроход с множителем Kспец: Kспец берётся из
  параметров зоны (`k_special`), при отсутствии — тарифный default
  (`special_passage_multiplier`); при протяжённости ≥
  `special_passage_min_len_m` участок выделяется отдельным объектом
  и считается по Kспец своей зоны.

Контуры самих ОКС временно блокируются, чтобы трасса не пересекала здания.

### 2.3. Точки врезки — строгое правило §8.2

Детерминированно, без эвристики кандидатов:

1. если от точки подключения до существующей камеры ≤
   `chamber_tap_max_dist_m` (10 м) и у камеры меньше
   `max_chamber_connections` (4) примыкающих участков — врезка в эту
   камеру (ближайшую из подходящих);
2. иначе — строительство новой камеры на ближайшей проекции точки
   подключения на существующий участок (в радиусе `tap_search_radius_m`);
   участков в радиусе нет — ОКС в `unconnected` (§2.9).

Камера ветвления ствола ограничена `max_new_directions_per_chamber` = 3
новыми направлениями — пачки ОКС нарезаются по этому лимиту.

### 2.4. Маршрутизация

Трасса — A* по весовой сетке (8 направлений, штраф за поворот
`turn_penalty_m`). Постобработка: упрощение полилинии (Рамер–Дуглас),
контроль самопересечений.

### 2.5. Мульти-ОКС и совместное подключение (§2.4)

ОКС кластеризуются по близости точек подключения (`cluster_radius_m`).
Кластер подключается общим стволом (несёт сумму расходов) с камерой
разветвления и ветвями до каждого ОКС. Проверка «деревянности» новой сети:
компонента из E рёбер и V вершин обязана удовлетворять E = V − 1.

### 2.6. Гидравлика (§2.4)

- Диаметр — минимальный Ду из справочника, чья пропускная способность
  покрывает расход участка.
- Предельная длина непрерывной части одного диаметра: при превышении
  участок делится техническим узлом, отсчёт начинается заново.

### 2.7. Реконструкция существующей сети (§2.6)

Добавленные расходы проталкиваются по цепочкам `next_object_id` к источнику.
Если требуемый Ду (по суммарному расходу) больше существующего — участок
попадает в перечень реконструкции (стоимость = `reconstruction_per_m_multiplier`
× стоимость новой прокладки). Камера с перегрузом примыканий — в перечень
реконструкции камер.

### 2.8. Варианты и ранжирование (§2.8)

Строятся до трёх **содержательно разных** вариантов (дубликаты отсекаются
по сигнатуре «набор врезок + набор трасс»):

1. **Совместное подключение, базовый коридор** — кластеры, общий ствол;
2. **Раздельное подключение** — каждый ОКС отдельной трассой;
3. **Совместное подключение, альтернативный коридор** — кластеры, но A*
   обходит коридоры трасс первых вариантов (веса ячеек в полосе
   `corridor_avoid_radius_m` вдоль уже построенных трасс повышаются в
   `corridor_avoid_factor` раза) плюс усиленный штраф за повороты.

Точка врезки строго по §8.2 детерминирована, поэтому вариантность
строится на топологии подключения (ствол/раздельно) и коридорах
маршрутизации, а не на выборе врезок.

Показатель: `score = 0,3 · стоимость/max + 0,7 · протяжённость/max`
(70% стоимость + 30% протяжённость строительных работ). Ранг 1 —
рекомендуемый вариант (`is_recommended`).

### 2.9. Стоимость (§2.7)

Калькуляция по ставкам `tariffs_rub`: новые участки (₽/м по диаметру,
спецпроход ×2,5), новые камеры, техузлы, врезки в существующие камеры,
реконструкция участков и камер, штраф за неподключённый ОКС
(`unconnected_penalty`).

### 2.10. Задание на глубину (доп. задача)

Для каждого нового участка строится вертикальный профиль (`app/engine/depth.py`):

- целевая глубина = `base_depth_m` + добавка по диаметру
  (`per_diameter_m`), квантование шагом `step_m` = **0,5 м**;
- ветвь, примыкающая к более глубокому стволу, «дотягивается» до его
  отметки пандусом с продольным уклоном не круче `max_slope_pct`;
- профиль непрерывен через технические узлы (конец подучастка = вход
  следующего);
- участки глубже `deep_threshold_m` — «глубокая прокладка», стоимость
  земляных работ ×`deep_multiplier`, факт уходит в `warnings`;
- камеры получают отметку дна: глубина примыкающего участка +
  `chamber_drop_m`.

Z записывается третьей координатой GeoJSON (метры, отрицательные —
ниже поверхности).

## 3. Обработка неподключённых ОКС (§2.9, частичный результат)

Расчёт **не падает** из-за отдельных ОКС:

| Ситуация | Поведение |
|---|---|
| Нет точек врезки в радиусе поиска | ОКС → `unconnected`, причина «нет доступных точек врезки» |
| A* не нашёл маршрут (запретные зоны) | ОКС → `unconnected`, причина «A* не нашёл маршрут…» |
| Часть кластера не подключилась | Остальные ОКС кластера считаются, вариант = `partial` |

Каждый неподключённый ОКС выводится объектом `unconnected` с причиной,
идёт в `metadata.unconnected_ids`, а в стоимость варианта добавляется
штраф `unconnected_penalty` — такой вариант честно проигрывает в рейтинге.

## 4. Выходные данные (§10 техприложения)

Единый GeoJSON `FeatureCollection` (EPSG:4326; по умолчанию **2D** — см. §6
ниже про режим заглубления). Верхний уровень — только `type` и `features`
(без `metadata` и `crs`). Все варианты — в одном файле: каждый объект несёт
`variant_id` (строка, "1" = лучший по §9).

Ровно семь типов объектов, у каждого — фиксированный набор атрибутов:

| `object_type` | Атрибуты (кроме id/object_type/variant_id) |
|---|---|
| `heat_network` | start_node_id, end_node_id, diameter, flow_tph, length_m, laying_method (base/special), depth_start/depth_end (null в 2D), cost_rub |
| `tie_in` | connected_oks_id, network_object_id, kind (existing_chamber/new_chamber), existing_diameter, cost_rub (5 000 000 ₽) |
| `heat_network_reconstruction` | existing_object_id, existing_diameter, required_diameter, existing_flow_tph, added_flow_tph, calculated_flow_tph, length_m, cost_rub |
| `heat_chamber` | diameter, cost_rub (шкала 3/5/8/12 млн ₽ по макс. Ду) |
| `heat_chamber_reconstruction` | chamber_id, existing_diameter, required_diameter, cost_rub |
| `technical_node` | reason |
| `variant_summary` | rank, score, calculated_cost, construction_cost, chamber_construction_cost, tie_in_cost, reconstruction_cost, chamber_reconstruction_cost, unconnected_penalty, length (new+reconstruction), new_network_length, reconstruction_length, connected/unconnected counts, unconnected_oks_ids; `geometry: null` |

Скоринг вариантов (§9): `S = 0,3·(C/25 000 000) + 0,7·(L/100)` (веса уточнены по протоколу 16.09.2026: в первичной редакции приложения они были перепутаны), меньше —
лучше; ранг 1 присваивается минимальному S.

---|---|
| `new_segment` | роль (trunk/branch), метод (open_trench/special_passage), Ду, расход, длина, **глубина min/max**, стоимость, warnings; геометрия LineString **с Z** |
| `new_chamber` | вид (врезка в трубу / разветвление), стоимость, **отметка дна** |
| `technical_node` | причина (предельная длина Ду…) |
| `tapping` | врезка в существующую камеру, расход, стоимость |
| `reconstruction_segment` | существующий/требуемый Ду, расходы, длина, стоимость |
| `reconstruction_chamber` | причина, стоимость |
| `unconnected` | ОКС, причина |

## 5. Границы применения

- Справочники диаметров (Ду 50–1400), тарифы, габариты и правила
  ограничений в `reference.yaml` соответствуют таблицам 4.1/4.2/5.1 и §8–9
  техприложения; заменяются конфигом без изменения кода (§2.14).
- Расчёт плановый: рельеф (отметки поверхности) не учитывается. Выгрузка
  по умолчанию 2D (depth_start/depth_end = null); режим заглубления §6
  (нормативная глубина, Kгл, техузлы на пересечениях) включается переменной
  `ENGINE_DEPTH_MODE=1` у контейнера app.
- Гидравлика — подбор Ду по пропускной способности; гидравлический расчёт
  (потери давления, пьезометрика) вне scope кейса.
- Совместное подключение — эвристика «кластер + общий ствол», не точное
  решение задачи Штейнера (см. риски плана).
- Входной набор — GeoJSON строго в EPSG:4326 (техприложение); файлы,
  объявляющие другую CRS, отклоняются на загрузке. Расчёты — EPSG:32637.
- Лимиты: вход до 3 ГБ (потоковый парсинг), результат до 500 МБ (стриминг),
  память сервисов ограничена в compose.

## 6. Проверка универсальности (§2.14)

- Никаких констант конкурсного набора в коде: идентификаторы, координаты,
  справочники — только из входного файла и `reference.yaml`.
- Смоук-тест `oracle/tests/run_engine_smoke.py` — 54 проверки (контракт
  §10, §3/§5.1/§6/§7/§8.2/§8.3/§9 + правила протокола 16.09.2026 п.7–п.9)
  на синтетическом наборе `oracle/tests/data/contest_sample.geojson`;
  E2E через Java API — `oracle/tests/e2e_api.py` (оба набора, контракт §10).
  Java-порт сверен с Python-оракулом численно: расхождение стоимости
  ≤ 0,015 %, score и ранжирование совпадают (см. Дельту, dit-sprint6.0-java).
- Дополнительный набор `tests/data/contest_sample_extra.geojson` (другой
  район, другая топология сети, кольцевая сеть, ОКС в запретной зоне) —
  репетиция по демо-сценарию, см. `docs/Демо-сценарий.md`.
