## 1. Архитектура

```
docker-compose.yml (совместим с docker-compose 1.29.2 и compose plugin v2)
│
├── app          Java 11 + Spring Boot 2.6.3 — ПУБЛИЧНАЯ ТОЧКА ВХОДА (:8080)
│                • REST API + springdoc-openapi-ui 1.7.0 (Swagger UI: /swagger-ui.html)
│                • загрузка GeoJSON до 3 ГБ: multipart-стриминг на диск
│                  (file-size-threshold: 0 — файл никогда не поднимается в память)
│                • очередь заданий, статусы, метаданные в PostgreSQL
│                • выгрузка результата до 500 МБ стримингом (InputStreamResource)
│                • раздача собранного фронтенда (страница /dit)
│
├── geo-engine   Python 3.11 + FastAPI — ВНУТРЕННИЙ (без публикации портов)
│                • расчётное ядро: граф сети, A* по весовой сетке, гидравлика,
│                  варианты, стоимость, вертикальный профиль
│                • потоковый парсинг входного GeoJSON (ijson, до 3 ГБ)
│
└── db           PostgreSQL 16 (≤18 по ТЗ)
```

Внешний мир видит только `app:8080`. Движок вызывается по внутренней сети
compose (`POST /engine/process`), обмен файлами — через общий volume `/exchange`.

### Запуск

```bash
git clone git@github.com:kirin2461/Hackaton29.09.2027.git heatnet-dit
cd heatnet-dit
docker-compose up --build        # или: docker compose up --build
# Swagger UI:  http://localhost:8080/swagger-ui.html
# Веб-страница: http://localhost:8080/dit
```

Целевая среда: Ubuntu Server 22.04, Docker, docker-compose 1.29.2,
16 ГБ RAM (потоковая обработка позволяет работать и на меньшем объёме —
в compose выставлены `mem_limit` для каждого сервиса).

### API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/jobs` | Загрузка конкурсного GeoJSON (multipart, поле `file`) → `202` + `id` |
| `GET` | `/api/jobs/{id}` | Статус задания: `QUEUED → PROCESSING → DONE / FAILED` |

## 2. Алгоритм

Расчёт — детерминированный конвейер (`geo-engine`, `app/engine/pipeline.py`).
Все справочники, тарифы и правила — во внешнем конфиге
`backend/app/engine/reference.yaml`, **не в коде** (§2.14): при выдаче
техприложения правится только YAML.

### 2.1. Загрузка и граф существующей сети

- Потоковый парсинг входного GeoJSON (ijson) — файл до 3 ГБ не поднимается
  в память целиком; автоматический подбор зоны UTM по центроиду набора.
- Из сегментов и камер строится граф существующей сети; цепочки
  `next_object_id` дают направление «к источнику» — используется для
  оценки реконструкции (§2.6).

### 2.2. Весовая сетка и ограничения (§2.5)

Область расчёта растеризуется с шагом `grid_cell_m` (5 м). Каждая ячейка
получает вес из зон ограничений входного набора:

- `forbidden` — ячейка запрещена (бесконечный вес);
- `min_distance` — буфер вокруг объекта запрещён;
- `crossing` — проход разрешён, но пересечение проверяется на угол
  (≥ `crossing_min_angle_deg`, иначе предупреждение);
- `special_passage` — проход с множителем стоимости
  (`special_passage_multiplier`), при протяжённости ≥ `special_passage_min_len_m`
  участок выделяется как спецпроход отдельным объектом.

Контуры самих ОКС временно блокируются, чтобы трасса не пересекала здания.

### 2.3. Точки врезки (§2.3)

В радиусе `tap_search_radius_m` ищутся кандидаты: существующие камеры
(с лимитом примыканий `max_chamber_connections` = 4, из них новых
направлений ≤ `max_new_directions_per_chamber` = 3) и проекции на сегменты
(врезка с постройкой новой камеры). Кандидаты ранжируются по стоимости
«врезка + прямая длина».

### 2.4. Маршрутизация

Трасса — A* по весовой сетке (8 направлений, штраф за поворот
`turn_penalty_m`). Постобработка: упрощение полилинии (Рамер–Дуглас),
контроль самопересечений, контроль углов пересечения зон `crossing`.

### 2.5. Мульти-ОКС и совместное подключение (§2.4)

ОКС кластеризуются по близости точек подключения (`cluster_radius_m`).
Кластер подключается общим стволом (несёт сумму расходов) с камерой
разветвления и ветвями до каждого ОКС. Проверка «деревянности» новой сети:
компонента из E рёбер и V вершин обязана удовлетворять E = V − 1.

### 2.6. Гидравлика (§2.4)

- Диаметр — минимальный Ду из справочника, чья пропускная способность
  покрывает расход участка.
- Предельная длина непрерывной части одного диаметра: при превышении
  участок делится техническим узлом, отсчёт начинается заново.

### 2.7. Реконструкция существующей сети (§2.6)

Добавленные расходы проталкиваются по цепочкам `next_object_id` к источнику.
Если требуемый Ду (по суммарному расходу) больше существующего — участок
попадает в перечень реконструкции (стоимость = `reconstruction_per_m_multiplier`
× стоимость новой прокладки). Камера с перегрузом примыканий — в перечень
реконструкции камер.

### 2.8. Варианты и ранжирование (§2.8)

Строятся до трёх **содержательно разных** вариантов (дубликаты отсекаются
по сигнатуре «набор врезок + набор трасс»):

1. **Совместное подключение, оптимальные врезки** — кластеры + лучшие точки врезки;
2. **Раздельное подключение** — каждый ОКС отдельной трассой;
3. **Совместное подключение, альтернативные врезки** — кластеры + вторые
   по рангу точки врезки.

Показатель: `score = 0,7 · стоимость/max + 0,3 · протяжённость/max`
(70% стоимость + 30% протяжённость строительных работ). Ранг 1 —
рекомендуемый вариант (`is_recommended`).

### 2.9. Стоимость (§2.7)

Калькуляция по ставкам `tariffs_rub`: новые участки (₽/м по диаметру,
спецпроход ×2,5), новые камеры, техузлы, врезки в существующие камеры,
реконструкция участков и камер, штраф за неподключённый ОКС
(`unconnected_penalty`).

### 2.10. Задание на глубину (доп. задача)

Для каждого нового участка строится вертикальный профиль (`app/engine/depth.py`):

- целевая глубина = `base_depth_m` + добавка по диаметру
  (`per_diameter_m`), квантование шагом `step_m` = **0,5 м**;
- ветвь, примыкающая к более глубокому стволу, «дотягивается» до его
  отметки пандусом с продольным уклоном не круче `max_slope_pct`;
- профиль непрерывен через технические узлы (конец подучастка = вход
  следующего);
- участки глубже `deep_threshold_m` — «глубокая прокладка», стоимость
  земляных работ ×`deep_multiplier`, факт уходит в `warnings`;
- камеры получают отметку дна: глубина примыкающего участка +
  `chamber_drop_m`.

Z записывается третьей координатой GeoJSON (метры, отрицательные —
ниже поверхности).

## 3. Обработка неподключённых ОКС (§2.9, частичный результат)

Расчёт **не падает** из-за отдельных ОКС:

| Ситуация | Поведение |
|---|---|
| Нет точек врезки в радиусе поиска | ОКС → `unconnected`, причина «нет доступных точек врезки» |
| A* не нашёл маршрут (запретные зоны) | ОКС → `unconnected`, причина «A* не нашёл маршрут…» |
| Часть кластера не подключилась | Остальные ОКС кластера считаются, вариант = `partial` |

Каждый неподключённый ОКС выводится объектом `unconnected` с причиной,
идёт в `metadata.unconnected_ids`, а в стоимость варианта добавляется
штраф `unconnected_penalty` — такой вариант честно проигрывает в рейтинге.

## 4. Выходные данные (§2.10)

Единый `FeatureCollection` (EPSG:4326, **3D** — у новых объектов есть Z):

- `metadata` — сводка: `engine`, `job_elapsed_ms`, `buildings_total/connected`,
  `unconnected_ids`, `costs_rub` (развёрнутая калькуляция), `length_total_m`,
  `warnings`, `variants[]` (ранг, label, score, is_recommended, статус,
  калькуляция, длина, счётчики объектов).
- `features[]` — объекты всех вариантов, каждый помечен `properties.variant`
  (ранг, 1 = рекомендуемый):

| `object_type` | Свойства |
|---|---|
| `new_segment` | роль (trunk/branch), метод (open_trench/special_passage), Ду, расход, длина, **глубина min/max**, стоимость, warnings; геометрия LineString **с Z** |
| `new_chamber` | вид (врезка в трубу / разветвление), стоимость, **отметка дна** |
| `technical_node` | причина (предельная длина Ду…) |
| `tapping` | врезка в существующую камеру, расход, стоимость |
| `reconstruction_segment` | существующий/требуемый Ду, расходы, длина, стоимость |
| `reconstruction_chamber` | причина, стоимость |
| `unconnected` | ОКС, причина |

## 5. Границы применения

- Справочники диаметров, тарифы и правила в `reference.yaml` —
  **инженерно-правдоподобные плейсхолдеры** до выдачи техприложения;
  заменяются конфигом без изменения кода (§2.14).
- Расчёт плановый: рельеф (отметки поверхности) не учитывается, Z — нормативная
  глубина заложения, а не проектный профиль по геодезии.
- Гидравлика — подбор Ду по пропускной способности; гидравлический расчёт
  (потери давления, пьезометрика) вне scope кейса.
- Совместное подключение — эвристика «кластер + общий ствол», не точное
  решение задачи Штейнера (см. риски плана).
- Входной набор — GeoJSON в любой проекции (авто-UTM); системы координат
  без корректного EPSG не поддерживаются.
- Лимиты: вход до 3 ГБ (потоковый парсинг), результат до 500 МБ (стриминг),
  память сервисов ограничена в compose.

- Никаких констант конкурсного набора в коде: идентификаторы, координаты,
  справочники — только из входного файла и `reference.yaml`.
- Смоук-тест `backend/tests/run_engine_smoke.py` — 19 проверок на
  синтетическом наборе `tests/data/contest_sample.geojson`.
- Дополнительный набор `tests/data/contest_sample_extra.geojson` (другой
  район, другая топология сети, кольцевая сеть, ОКС в запретной зоне) —
  репетиция по демо-сценарию, см. `docs/Демо-сценарий.md`.
